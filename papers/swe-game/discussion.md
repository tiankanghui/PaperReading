# 问题与关键点

## 评测靠视觉，还是靠代码？

功能正确性主要由运行时测试判断：评测器发送操作，通过语义接口读取碰撞、健康值、进度等引擎状态，检查行为是否满足要求。项目结构、内容、素材使用和接口有效性也参与检查。

视觉质量由 VLM 根据候选游戏帧、参考帧与游戏专属 rubric 评分。三类构建任务中，客观组件占 85%，视觉组件占 15%；客观组件并不等于让模型阅读源代码打分。

依据：§3.3–3.4；附录 C、D、H.6。

## 如何判断演示是真的有效？

Agent 提交的功能演示是动作序列，必须由评测器重新执行。每段演示从新的启动状态开始，并与匹配时长的无输入运行比较；若没有操作也能达成相应目标，该结果不能获得相应的演示分数。重复演示不能增加覆盖。

独立演示可以分别展示跳跃、拾取、失败与重试，不要求每段都完成全游戏。参考回放另行检查规定目标与中间里程碑。

依据：§3.4；附录 H.2。

## 是否包含端到端游戏开发？

Brief-to-Game 从简短目标、素材和参考视频出发，要求完成自编设计文档、可运行 Godot 项目和功能演示。GDD-to-Game 提供详细设计，仍要求完成规定游戏。

范围限于预先限定的小游戏和素材，不包含从零制作全部资源或长期商业开发。Skeleton Completion 使用新生成的最小集成脚手架，不是从成熟参考项目删除部分代码。

依据：§3.2；附录 B.1、B.3、H.1–H.3。

## 哪些能力值得优先关注？

需求覆盖、机制与状态逻辑、引擎集成和执行验证，是当前结果提示的重要关注点。已分类问题中，GPT 与 Opus 以需求遗漏为主，GLM 以玩法逻辑问题为主；这些占比不是所有任务的失败率。

实践上可以为每个机制建立“触发条件 → 状态变化 → 玩家反馈 → 失败与恢复”的检查项，再验证机制组合、重启与跨关卡状态。这是基于论文形成的建议，并非作者已单独验证的提升方法。

实验比较模型与各自 Agent 框架的组合，不能独立确定规划、视觉理解、编程或测试能力对成绩的因果贡献。

依据：§4.1–4.3；表 3；局限，第 10 页。
