# 游戏能跑起来，玩法就做对了吗？

SWE-Game 关注的是游戏开发中一个具体的落差：Agent 能做出可启动、看起来像样的项目，但它是否实现了玩家要求的规则、内容与反馈？作者通过可执行参考游戏建立目标，再结合运行时测试和视觉评分回答这个问题。

> 初读笔记 · 2026-10-27。基于 arXiv v3 正文及相关附录；评测代码尚未核查，记录随后续阅读修订。

## 研究问题

论文在引言中举了一个例子：画面里有尖刺，玩家碰到后却不受伤。外观相似不能证明玩法正确；出现胜利画面，也不能证明规定的交互真的发生过。

评测需要把需求转化成可观察的行为：玩家做了什么，游戏状态怎样变化，是否产生了预期结果。视觉质量则需要另一组证据。

## 五类任务，也有端到端开发

基准包含 41 个 Godot 参考游戏：24 个 2D、17 个 3D，覆盖 13 类玩法。它们派生出 247 个任务。

- **Brief-to-Game，41 个：** 给简短目标、素材和参考视频，Agent 先写游戏设计文档（GDD），再开发游戏并提交功能演示。考察设计到实现的完整过程。
- **GDD-to-Game，41 个：** 给完整设计文档、素材和参考视频，考察详细需求的落实。
- **Skeleton Completion，41 个：** 在最小脚手架上补全游戏，考察实现与接口集成。
- **Bug Repair，83 个：** 给故障项目、玩家症状报告和需求，考察定位、修复与行为保留；不提供参考视频。
- **Godot-to-Unity Porting，41 个：** 给 Godot 项目及参考材料，要求在 Unity 中实现并保持原有玩法。

Brief-to-Game 和 GDD-to-Game 都包含完整游戏构建，但素材与小游戏范围已经给定。这里的端到端不包含从零制作全部素材、长期产品开发或商业发行。

Skeleton 是新生成的最小集成脚手架，不是把成熟参考项目挖掉几段代码。因此它对大型既有代码库理解能力的考察有限。（§3.2；附录 B.1、B.3）

## Judge：执行证据为主，视觉评分补充

功能评测主要由评测程序运行游戏、发送动作、读取引擎状态并检查结果完成，不是让大模型阅读源代码打分。另有内容、素材使用、项目结构和接口有效性等检查。

不同 Agent 的对象名和代码结构不同。统一的 instrumentation 接口要求提交方声明玩家、危险物、输入动作、健康值等语义绑定；评测方验证绑定，再用自己的驱动与探针执行检查。

碰刺扣血的例子可以理解为：

> 找到玩家和尖刺 → 执行接触 → 观察碰撞及健康值变化 → 检查死亡或重生行为。

测试和预期结果由评测方掌握，提交方提供的是绑定。评测允许不同实现，而不要求代码与参考项目相同。（§3.3；附录 C，表 7）

## 回放与无输入对照

评测使用两类操作序列。**参考回放**是在参考游戏上验证过的动作，检查目标及中间里程碑；**Agent 编写的功能演示**则展示候选游戏中的特定机制，由评测器独立重放。演示是操作序列，不是 Agent 自报分数。

每次演示从新的启动状态开始，并运行匹配时长的无输入对照。如果不操作也能达到相应目标，该结果就不能获得相应的回放或演示分数。重复演示不能增加功能覆盖。

独立功能演示不要求每一段都完成全游戏，跳跃、拾取、失败与重试可以分别展示；参考路线另行检查目标与里程碑。（§3.4；附录 H.2）

## 视觉如何评分

VLM 接收评测器选取的候选游戏帧、参考帧、素材图和游戏专属评分规则（rubric）。它逐项评价可见玩法、内容组织、引导反馈和画面表现，返回结构化判断、依据帧及缺陷；宿主程序应用计分规则和缺陷分数上限。

画面无法认证隐藏代码、精确输入延迟或未观察到的碰撞。三类构建任务的最终分数由 **85% 客观组件和 15% VLM 视觉组件**组成。85% 不能直接称为“代码分”，修复与迁移任务也不套用同一公式。（§3.4；附录 D、H.6）

## 实验揭示的两个落差

**能操作，不代表规定机制完整。** 六组模型与 Agent 框架配置中，Opus5 在五类任务的总分均最高；三类构建任务最高分仍低于 60：简短目标开发 50.38、GDD 开发 59.68、脚手架补全 54.06。在 GDD 开发中，Opus5 的 Playability 为 91.94，而 Mechanics 为 32.96，说明两种评分维度关注的内容不同。（表 3）

**写好设计文档，不代表实现到位。** Brief-to-Game 中，GPT-5.6 Luna 的 Design 为 92.68，总分为 34.18。设计需要落实为可检查的游戏行为，不能只停留在文档。（表 3）

作者分析的已分类问题中，GPT 与 Opus 最常见的是需求遗漏，占比分别为 56.4% 和 36.9%；GLM 最常见的是玩法逻辑错误，占 52.2%。这是各模型问题的构成比例，不是任务失败率。（§4.3）

作者还验证了 judge 本身：在 100 个 Agent 构建游戏的 1,200 条人工标注断言上，可执行检查的平衡准确率为 92.59%，视频 VLM judge 约为 78.41%；在 200 段视频上，视觉 rubric 分数与人工评分的 Spearman 相关系数为 0.829。92.59% 是评测器判断正确性的指标，不是游戏开发成功率。（§4.5，表 5）

## 对游戏 Agent 的启发

**我的初步判断：** 优先关注需求覆盖、机制和状态逻辑、引擎集成，以及真实执行验证。碰刺扣血不仅涉及一段扣血代码，还涉及碰撞连接、死亡、重生和状态重置。

一个值得尝试的工作方式，是为每个机制写下：

> 触发条件 → 状态变化 → 玩家反馈 → 失败与恢复。

逐项实现和验证，再测试机制组合、重启与跨关卡状态。这是基于论文形成的实践建议，论文没有单独验证这种流程能提高多少分。

榜单比较的是模型与各自 Agent 框架的组合，工具与资源使用也不同。它不能独立量化规划、视觉理解、编程或测试能力的因果贡献。（§4.1；局限，第 10 页）
