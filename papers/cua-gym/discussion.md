# 问题与关键点

## 数据构造的核心难点为什么不是多写一些任务？

电脑操作题需要一个可操作的世界和与需求一致的判分标准。任务要求给客户发送带交易附件的邮件，环境就必须有客户、地址、模板、交易资料和可用邮箱；奖励必须核对发送结果，而非只看“出现了一封邮件”。指令、环境、奖励中的任何一方错位，都会让训练信号失真。

CUA-Gym 因此把基本数据单元定义为任务包 `(t, s, r)`，将教师操作轨迹放在其后的训练阶段。功能树与场景矩阵负责组织能力覆盖；初始/目标脚本负责落实世界；奖励与筛选负责检查可用性。依据：第 1、2.1 节，PDF 第 1–3 页；附录 A.2、A.6，PDF 第 14–16、20–21 页。

## 怎样理解功能树、覆盖矩阵与三轮生成？

功能树拆分应用的操作能力，场景矩阵组合平台、领域、难度、使用情境和单/跨应用类型。第一轮铺开叶子，第二轮根据统计补缺口，第三轮从失败与少见操作中构造边界任务。逆频率采样让不足的组合更容易被抽到，避免全部预算落在几个常见功能上。

文本去重只能防止高度相似的问句；能力是否真正多样，还要看任务是否要求不同的状态变化或工作流。只替换客户姓名与数字，不能直接说明获得了更广的能力覆盖。这是对采样机制的解释。附录中的每应用和每叶配额与其他数字不一致，不能作为已经实现的生产分布引用。依据：附录 A.2，PDF 第 14–16 页。

## 判分 Agent 究竟看得到什么，信息隔离有何作用？

它不能读 Generator 的初始/目标脚本与工作目录，但能读取任务、上下文、领域技能，以及通过状态 API 查看两个 VM 的结果。不能把“从需求独立写 reward”解释为完全看不到目标状态。

隔离的作用是减少奖励依赖构造脚本的捷径，使验证条件尽量来自任务语义。它没有消除对 golden 的观察，也不能证明所有隐藏常量、宽松匹配或代理指标都不存在。原文在局限中同样承认残余奖励漏洞。依据：正文第 2.1 节、附录 Table 1 与 G.4，PDF 第 3、17、79 页；第 6 节，PDF 第 10 页。

## 初始得 0、目标得 1，为什么还不能认定奖励可靠？

这两个条件仅证明奖励能区分这一对状态。一个检查文件存在和若干关键词的奖励，可能拒绝原始输入并接受 golden，却同时接受内容错误的另一份文件。静态扫描能排除部分明显捷径，但不能穷尽语义错误。

内循环适合发现生成与判分的具体错位。附录的双场景任务中，两个脚本均运行成功，但目标文件把 Optimistic 写成了 Pessimistic 数值；奖励给 0.65 并定位错误，修复后才达到 1。真正的“对抗”体现在独立核对和诊断，不是训练一个 GAN，也不是让 Generator 专门寻找欺骗奖励的失败状态。

更强的反例验证可以故意制造错误收件人、漏附件、错值或破坏输入等状态，再检查奖励是否拒绝。这是根据当前保证范围提出的建议，不能写成原文已完成的实验。依据：附录 A.3、E.4，PDF 第 16–17、69–70 页。

## 如何判断失败后应该修 setup 还是 reward？

目标得不到满分本身无法定位错误。如果目标场景的单元格值写错，应修 golden；如果奖励把初始就存在的模板邮件当成已完成发送，应修 reward。初始得正分也可能来自 setup 提前放入完成产物。先核对需求、实际状态和各评分组件，才能决定修复方向。

五个内循环条件是程序检查，`REVIEW.md` 传递结果而非代替实际运行。原文 A.3.3 明确把禁止模式反馈给 Discriminator；G.3 的目标低分反馈模板则要求 Generator 修改 golden。由此提出的判断是：端点低分只能触发诊断，不能自动证明奖励正确。外层 critic 会再拒绝无法仅靠改写指令修复的 setup/reward 缺陷。依据：附录 A.3.3、G.3、G.5/G.6，PDF 第 16–17、78、80–81 页。

## 为什么奖励应只给新增变化计分？

如果 Summary 初始就可见，奖励单独为其可见给分，会让未执行任何操作的策略获得正奖励。任务要求隐藏 Raw Data 时，新增变化才是 Raw Data 的隐藏；Summary 保持可见可以与该变化共同构成约束。原有数据完整性也应作为失败时归零的门槛，而不是独立奖分项。

“增量”指由任务要求决定的新状态，不是对所有 diff 发奖励。不必要地删改其他数据也是变化，反而可能应使结果无效。依据：附录 G.4，PDF 第 79 页；状态 diff 规范在 B.3，PDF 第 25–26 页。

## 真实 rollout 与 VLM 判分怎样补足程序检查？

Golden 可以用代码直接写出，教师却要通过 GUI 从初始状态达到目标。Rollout 因而检查 UI 是否可达、任务是否自洽和步数内是否可完成。程序奖励看结构化状态、文件内容；VLM 看最终视觉结果，帮助发现程序漏掉的可见问题。

两者分数明显偏离时，样本反馈给奖励作者修订并重测。双零视为可能不可解，首次双一视为可能过简单，分别删除或降采样。但教师失败不是不可解证明，两个判分器一致也可能共享盲点。文中未给出具体教师试验数与对照容差，因此只能准确说明机制，无法还原完整筛选配置。依据：附录 A.4，PDF 第 17–18 页。

## mock 的状态注入、diff 与会话隔离各解决什么？

状态注入解决同一个应用如何承载多道题：代码不变，业务实体和初始数据改变。Diff 解决怎样把 UI 后果转成程序可检查的变化。会话隔离解决多个 worker 同时执行时如何避免互相污染。

`set` 写初始快照，`set_current` 写当前快照，奖励通过 `/go` 读取两者的变化。若弄混这两个写入方向，就可能把完成状态覆盖成基线，导致 diff 失去任务变化。数组变化被整体记录时，奖励仍需检查实际实体和值，不能只看某个 key 存在。

这使 reward 可以检查最终业务结果，允许不同 UI 路径完成任务。但终态相同并不保证过程无破坏；mock 的确定性后端也没有涵盖真实认证、网络和权限故障。依据：正文第 2.2 节、Figure 3，PDF 第 4–5 页；附录 B.3，PDF 第 25–26 页；第 6 节，PDF 第 10 页。

## 环境多样性是否已经被直接证明能改善 RL？

论文有两组不同证据。固定 SFT 初始化后，用 1.4K、3K、12K 任务包进行 RL，支持任务量扩展。环境数对照则用成功教师轨迹 SFT：固定 3K 轨迹，10→80 个环境将 OSWorld-Verified 从 57.8% 提高到 58.8%；固定 80 个环境，3K→6K 轨迹再提高到 60.7%。

这些结果支持环境覆盖与样本量各有价值，但环境多样性的净作用是在教师蒸馏设置下测得，不能称为直接的 RL 环境消融。首尾 2.9 个百分点同时包含覆盖与数据量变化。依据：第 4.1、4.2 节，Figures 7、8，PDF 第 7–9 页。

## 最应保留的判断边界是什么？

这套 pipeline 的价值在于把“多样、可执行、自洽、可解、可判分”拆成不同检查层，使生成任务可以持续进入后训练。程序化奖励有利于稳定优化，却不自动等于完整理解任务。两端检查、多数审查与教师 rollout 是实用的证据累积，不是形式化完备性保证。

正文表现支持所研究范围内的桌面与浏览器迁移；mock 与真实服务的差距、教师筛选偏差、单 seed 和版本内部数字不一致仍限制结论。对复现来说，应优先核查具体访问权限、筛选参数、语义反例和数据分布，而非直接照抄附录配额。依据：第 6 节，PDF 第 10 页；附录 A.2、A.4，PDF 第 14–18 页。
