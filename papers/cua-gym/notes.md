# 一句话理解

CUA-Gym 要解决的是：**怎样批量准备电脑操作练习，让 Agent 有材料可用、有任务可做，做完还能自动判分？** 它为每道题一起生成任务要求、操作前的电脑环境和检查结果的程序，再反复检查、让 Agent 真正尝试，把可用的题留下来用于训练。

## 1. Motivation：为什么需要解决这个问题

数学任务通常可以给出题目并检查答案，代码任务可以运行测试。电脑操作任务多了一层：首先要有一个可操作的世界。要求“给客户发邮件并附上交易表”，必须预先存在客户名单、地址、模板、交易文件、邮箱状态和可用界面；判分还要检查收件人、正文与附件是否一致。只有一句自然语言指令，无法直接成为 RL 数据。

原文在第 1 节把一道题写成 `(t, s, r)`：`t` 是要做的事，`s` 是操作开始前的电脑环境，`r` 是检查结果并打分的程序。三者必须配合：起点中如果已经完成了任务，Agent 不操作也能得分；界面做不到要求的操作，这道题就无解；程序只检查文件名，创建一个同名空文件也可能蒙混过关。

另一个瓶颈是应用覆盖。真实网站涉及登录、限流、外部服务和不断变化的状态，难以反复恢复到同一状态供大量操作练习使用。人工维护少数应用可以获得可靠判分，却很难覆盖长尾工作流。CUA-Gym 同时扩大任务数量和可控环境数量。依据：正文第 1、2 节，PDF 第 1–4 页。

## 2. Insight：最值得记住的想法

**出一道题，需要同时准备题目、材料和判分办法。** 例如练习发邮件，就要有客户名单和邮箱界面，也要能检查发给了谁。CUA-Gym 把这几件事放在一起生成和检查，避免题目要求的东西在电脑里不存在。

**自动判分还需要检查是否判对。** 一段代码每次都给同样的分数，不代表它检查得完整。只看邮件数量，可能漏掉错误收件人；所以论文既检查判分代码，也让 Agent 实际操作后再核对结果。

**同一个训练网站可以反复换材料出题。** 同一套邮箱界面装入不同邮件和客户资料，就能练习不同任务；增加表格、项目管理等其他应用，则能练到新的操作。CUA-Gym-Hub 提供这些训练网站，CUA-Gym 在它们上面准备具体练习题。依据：正文第 2 节，PDF 第 3–4 页；第 6 节，PDF 第 10 页。

## 3. Method：训练任务是怎样一步步生成的

### 3.1 先用“给客户发邮件”看懂主图

假设要让 Agent 完成这件事：**从 Notion 的客户名单中找到每位客户的邮箱，按照 Gmail 中的模板写邮件，并附上桌面表格里属于该客户的交易记录。** Notion 是存放客户名单的应用，Gmail 是发邮件的应用。主图用的就是这样一项需要同时使用多个软件的任务。

要把它用于训练，首先需要准备三样东西：

- **要做什么：** 上面这句发邮件的要求，称为“任务指令”。
- **从哪里开始做：** 电脑里已有客户名单、模板和交易表，相关页面也已打开，但任务要求的新邮件还没有发出。这称为“初始环境”。
- **怎样判断做对了：** 一段检查程序，核对邮件是否发给了指定客户，内容和附件是否正确。这称为“奖励函数”，这里可以先把它理解为“判分程序”。

**“环境状态”就是电脑里某一时刻实际有什么。** 例如文件是否存在、客户名单有哪些人、邮件是否已发送、当前打开哪个页面，都是状态的一部分。“把名单和模板准备好”只是一项要求；它们真正存在于电脑里，才是已经准备好的状态。

![给客户发邮件的任务，先准备两台电脑并编写判分程序，再经过审查与真实操作筛选。来源：原论文 Figure 1，PDF 第 3 页。](images/overview.png)

看这张图，可以按下面六步走：

**第一步，看左侧 Tasks：先写清要做什么，还需要哪些材料。** 图中的 Task 是给客户发邮件的要求；Context 是给准备环境的人看的材料清单：Notion 中要有 10 位客户及邮箱，Gmail 的“已发送”文件夹中要有可用模板，桌面交易表要包含规定时间范围的数据。图中的任务说明由这两部分组成：操作目标，以及准备材料的要求。

**第二步，看中间 Generator 下的两台电脑：分别准备“做之前”和“做对之后”的样子。** 左边的 Initial Env 中，名单、模板、表格已经齐备，新邮件尚未发出。右边的 Golden Env 中，则已经有任务正确完成后的结果。论文用两台彼此分开的虚拟电脑，也就是 VM，保存这两种情况。

**第三步，看中间 Discriminator：另一个 Agent 编写判分程序。** 它需要把“邮件发对了”拆成可检查的事项，例如收件人是否对应客户名单、内容是否符合模板、附件是否对应客户交易。图中 Information Isolation 的意思是：这个 Agent 可以查看两台电脑的结果，但看不到前一个 Agent 用来准备它们的脚本。这样它应当根据任务要求判分，减少照着生成脚本编检查的机会。

**第四步，看中间的反馈箭头：用两台电脑测试判分程序，再修问题。** “做之前”的电脑应该得 0 分；“正确完成”的电脑应该得 1 分，也就是满分。如果尚未发邮件就得了分，或者正确结果得不到满分，就要查明是哪边出了问题：材料准备错了、正确结果做错了，还是检查程序写错了。修好后再测。

**第五步，看右侧 Filter：审查后，再让 Agent 真正操作一次。** 先请其他模型检查任务说明是否含糊、准备的材料是否够用、判分标准是否合理。然后让能力较强的 Agent 从“做之前”的电脑开始，实际点击、填写和发送邮件。操作结束后，一边用程序检查文件和应用数据，一边用能看图的模型检查最终截图，比较两种判断是否接近。这一步可以发现“脚本能写出正确结果，但在界面上根本做不到”等问题。

**第六步，看右下角输出：把通过检查的一道题保存起来。** 保存的不只是一句话，还包括重新准备初始电脑的方法和判分程序。以后训练 Agent 时，就能反复回到同一个起点，让它尝试操作，再给结果打分。本文把这样整理好的一道题称为“任务包”。

```text
写清要做什么、需要哪些材料
  -> 准备“做之前”和“正确完成后”的两台电脑
  -> 另一个 Agent 编写判分程序
  -> 测试：做之前得 0，正确完成后得 1；有问题就修
  -> 检查任务说明，再让 Agent 通过界面真正尝试
  -> 保存题目、初始电脑的准备方法和判分程序
```

图顶端的 Orchestrator 负责安排上述步骤：准备电脑、分派工作、收集检查结果、决定是否再修一轮。先理解它是协调流程的 Agent 即可。

依据：正文第 2.1 节，PDF 第 3–4 页；附录 Algorithm 1，PDF 第 14 页。

### 3.2 怎样出很多不同的题，而不是反复换名字

如果让模型自由出题，可能会生成大量“给某人发邮件”或“修改某列格式”，却漏掉软件里许多其他功能。论文先整理软件能做什么，再统计哪些类型的题还太少。

**先整理功能清单。** 从软件文档和实际使用方式中，把功能按层级分组。例如表格软件可以按“格式 → 单元格外观 → 条件格式”展开，最末一层写清具体操作和涉及的按钮、菜单。这种有层级的清单在论文里叫“功能树”。出题时挑其中的具体功能，便知道这道题主要练什么。

**再按五类属性统计题目。** 看它用桌面还是网页、属于什么领域、难度如何、用于商业还是科研等场景，以及需要一个还是多个应用。把这些属性组合起来，就是论文的“场景矩阵”。某种组合已经有很多题，就少生成一些；某种组合很少，就多补一些。这就是“逆频率采样”的作用。少见应用也设最低数量，避免全部题目集中到最常用的软件。

出题分三轮：

- **先铺开：** 尽量让功能清单中的不同操作都有题可练。
- **再补缺：** 统计第一轮漏了什么，补充数量不足的类型，增加困难题和需要多个软件配合的题。
- **最后补特殊情况：** 根据此前失败的任务，加入少见的软件组合、拖拽、组合快捷键和多窗口操作等题目。

论文还检查题目文字是否重复：既比较两句话的意思是否很接近，也比较连续四个词的片段是否大量重合；同一应用中的一种句式模板最多保留 3 个实例。附录使用的阈值分别是句向量相似度 ≥0.85、四词片段重合超过 50%。这些检查限制文字重复；是否练到了新能力，仍要看实际操作有没有变化。只替换客户姓名，不一定增加新的操作能力。

最后，每道题都会有两份说明：**给执行者看的任务要求，以及给环境准备者看的材料清单。** 论文分别记为 `t` 和 `c`。材料清单帮助准备电脑；执行者能否仅凭自己看到的指令和材料理解任务，还要在后续审查中检查。

依据：正文第 2.1 节，PDF 第 3 页；附录 A.2、G.2，PDF 第 14–16、76–77 页。

### 3.3 怎样准备“做之前”和“正确完成后”的电脑

准备环境的 Agent，也就是图中的 Generator，读取任务要求、材料清单，以及该应用的操作和编程说明，然后写两个脚本：

| 脚本 | 做什么 | 邮件任务中的例子 |
| --- | --- | --- |
| `initial_setup.py` | 准备任务开始前的电脑 | 放好客户名单、模板和交易表，打开需要的页面；任务邮件尚未发出 |
| `golden_patch.py` | 在另一台电脑里准备正确完成后的结果 | 建立任务所要求的已发送邮件及附件 |

**正确完成后的电脑主要用来测试判分程序。** Generator 可以直接用代码写文件或修改应用数据；被训练的 Agent 则要通过界面操作。因此，这台电脑没有告诉 Agent 应该按什么顺序点击，也没有证明那些点击真的能完成任务。后面让 Agent 实际尝试，就是要补查这一点。

初始电脑还必须能直接开始操作。文件不仅要放到磁盘里，所需应用和文件也要打开；保存、恢复、安全提示等弹窗不能挡住界面。否则题目写着“在已打开的表格中修改”，Agent 看到的却是另一种情况。

两台电脑应使用相同的客户、模板和交易资料，差别只来自任务要求的操作。否则判分程序可能把无关差异当成完成证据。G.3 要求正确结果在目标电脑内独立构造，禁止从初始电脑直接加载或复制文件。

依据：正文第 2.1 节，PDF 第 3 页；附录 A.5、G.3，PDF 第 19–20、77–78 页。

### 3.4 为什么让另一个 Agent 写判分程序

如果同一个 Agent 既准备正确结果，又写判分程序，检查可能变成“确认我刚才写入的那个东西存在”。例如，它可能只认某个文件名，却不检查文件内容是否真的满足任务。

论文因此让另一个 Agent，也就是 Discriminator，来写 `reward.py`。它能读任务要求、材料清单和应用说明，也能通过规定的接口查看两台电脑中的文件与应用数据；但不能读 Generator 的脚本和工作目录，也不能把电脑里的任务文件下载到本地绕开限制。**隔开的是生成脚本；正确结果本身仍然可以查看。**

在邮件例子中，检查要围绕具体要求展开：从客户名单确定应该给谁发，从模板确定正文要求，从表格找到该客户的交易，再核对已发送邮件与附件的对应关系。仅检查“发送了十封邮件”不够，因为可能全部寄给同一个人；仅检查“附件存在”也不够，因为附件可能为空或属于其他客户。

判分可以拆成多项，完成一部分就得到一部分分数，总分在 0 到 1 之间。这样训练时，未完全完成任务的尝试也有区别，而不是全部得零分。具体分项和权重由每项任务的判分代码决定。

**已经存在的东西不能单独给分。** 例如图中的模板原本就在“已发送”文件夹里，它是任务材料，不是这次完成任务的结果。如果程序只要看见该文件夹里有邮件就给分，Agent 什么都不做也能得分。

原文还用隐藏工作表举例：任务要求隐藏 Raw Data，而 Summary 原本就可见。那么“Summary 可见”不能单独给分；可以检查“Raw Data 已隐藏，而且 Summary 仍保持可见”。同样，“文件没有损坏”可以作为判分前必须满足的条件，却不应成为未操作就能拿到的奖励。

应用数据发生变化，也不一定应该得分。把无关客户删除是一种变化，却没有完成发邮件的任务。评分项应对应任务要求的新结果。依据：附录 A.3.2、G.4，PDF 第 16–17、79 页。

### 3.5 怎样发现准备和判分中的错误

准备好两台电脑和判分程序后，先检查五件事。这是图中反复修复的部分，论文称为“内循环”。

| 原文条件 | 实际检查 | 为什么要检查 |
| --- | --- | --- |
| C1 | 准备初始电脑的脚本能否运行完 | 脚本报错，Agent 就没有可用的起点 |
| C2 | 准备正确结果的脚本能否运行完 | 脚本报错，就没有可用于测试的正确结果 |
| C3 | 正确完成后的电脑是否得 1 分 | 目标结果或判分程序可能有问题 |
| C4 | 还没做任务的电脑是否得 0 分 | 防止题目已被完成，或程序为原有材料给分 |
| C5 | 判分代码是否包含明显偷懒的检查 | 防止固定返回满分、只看文件存在等做法 |

前四项实际执行脚本和判分程序；第五项检查代码。论文列出的禁止写法包括直接把验证标志设为 True、没有真正检查就给分、固定返回成功分、仅凭文件存在给分、调用外部进程，以及只有注释声称检查过却没有相应代码。它用文本匹配和 Python 代码结构分析寻找这些写法；通过检查不等于排除了所有错误判分。

失败后会生成 `REVIEW.md`，记录哪项没过、两台电脑分别得多少分，以及修复建议。协调流程的 Agent 安排下一轮，最多修 5 轮；仍不过关就丢弃这道题。

**得不到满分，需要先查原因。** 正确结果里填错了数据，应修构造脚本；程序把已有模板当成新邮件，应修判分代码。原文对禁止写法会重新提示 Discriminator，对目标结果错误则反馈给 Generator。不能只凭“目标得不到满分”，就认定一定是目标做错了。

附录 E.4 给出一个具体例子：任务要求在表格中添加 Optimistic 和 Pessimistic 两个场景，每个场景保存五个单元格值。第一轮虽然添加了两个正确名称，却把 Optimistic 的值误写成了 Pessimistic 的值。判分程序检查表格内部保存的数据，只给 0.65：名称得 0.30，正确的 Pessimistic 得 0.35，错误的 Optimistic 丢失 0.35。反馈指出错误值后，第二轮修复，正确结果才得到 1，初始文件得到 0。

**两台电脑得 0 和 1，只说明程序在这两种情况上判对了。** 它仍可能接受“发给错误客户但附件名正确”等其他错误结果。要更可靠，还需要测试各种错误情况；这是根据保证范围提出的改进建议，论文没有报告系统的反例测试。

依据：附录 A.3、E.4、G.5，PDF 第 16–17、69–70、80 页。

### 3.6 为什么还要让 Agent 真正尝试操作

前面的检查可以确认材料和判分在两个测试结果上是否配合，但还没有确认题目能否在界面上完成。例如，Generator 直接用代码写出了某种表格效果，可是当前软件的菜单根本不支持它；或者任务要求引用一个执行者看不到的模板。

论文接着做两类筛选。

**先检查题目本身。** 来自不同模型家族的审查者检查任务是否说清楚、材料是否齐全、是否能执行，以及判分是否容易被错误结果蒙混。多数审查者同意才进入下一步，平票拒绝。这一步可以改写含糊的任务指令；若需要修改材料准备脚本或判分代码才能修好，审查者应拒绝，而不是只改措辞让它过关。

**再让较强的 Agent 实际做题。** 论文把这个执行者称为“教师”。它从初始电脑开始，通过界面尝试完成任务。这样的一次完整尝试叫一次 `rollout`；其中的截图和点击、输入等记录叫“轨迹”。后文使用这些词时，指的都是实际操作的尝试及其记录。

每次尝试结束后，用两种方法判断结果：

- **程序判分：** 检查文件内容、收件人、应用数据等具体结果。
- **看图判分：** 另一个能看图的模型，也就是 VLM，根据任务、检查清单和最终截图判断是否完成。例如表格数值正确，却缺了图表坐标轴标签，截图检查可能发现程序遗漏的问题。

原文根据多次尝试的平均分处理任务：两种判断都为零，视为可能做不到并删除；首次尝试两种判断都满分，视为可能太容易，减少这类题的数量；两个平均分都处于中间且相差很小时接受。差异明显则把问题反馈给判分 Agent，修改后重试，最多两轮修订。

这里的“可能”很关键：较强 Agent 失败，仍可能只是它能力不足；两个判分方法意见一致，也可能共同漏掉问题。论文没有给出尝试次数和允许的分数差，所以这些筛选规则还不足以精确复现。

依据：正文第 2.1 节，PDF 第 3–4 页；附录 A.4、G.6，PDF 第 17–18、80–81 页。

### 3.7 如果可用软件太少，怎样增加练习环境

上面讲的是已有软件中如何生成题目。但如果只准备了少数几个软件，再多出题也很难练到其他应用的操作。CUA-Gym-Hub 因此制作了一批**模仿真实网站界面和常用功能的训练网站**，论文称为网页 `mock`。

例如，一个训练邮箱可以显示邮件、支持写信和添加附件，却不需要真的连接外部邮箱服务器。它的价值是容易反复准备和重置，可以让许多 Agent 同时练习；真实登录、网络通信、第三方集成等复杂行为则被简化了。

![先研究目标网站，再开发训练网站，最后逐项测试按钮与页面；发现问题就返回修改。来源：原论文 Figure 2，PDF 第 4 页。](images/environment-pipeline.png)

这张图也可以按工作内容看：左侧 Plan Agent 研究真实应用，写清需要哪些页面、按钮和数据；中间 Dev Agent 按说明开发；右侧 Web Agent 用浏览器逐个操作，检查功能是否实现、页面是否符合参考，并报告“按钮点击后没反应”或“界面改了但后台没记住”等问题。开发者修好后再测试，直到没有严重问题或次数预算用尽。没修好的应用暂不进入发布集合。

应用选择参考两种资料：O*NET 的职业任务分类帮助决定需要哪些工作场景，Anthropic Economic Index 的软件使用分布帮助选择场景中的产品。最终，每个训练网站附带数据读写方法和应用说明，让前面负责出题、准备材料和判分的 Agent 能继续使用它。

依据：正文第 2.2 节，PDF 第 4–5 页；附录 B.2、B.4，PDF 第 22–24、26–27 页。

### 3.8 同一个训练网站，怎样放入不同材料并重新开始

同一个邮箱网站可以装入不同邮件：一次是空收件箱，一次是临近截止日的项目讨论，另一次是长期未处理的积压邮件。把这些数据写进网站，就是“状态注入”：界面代码仍是同一套，但这次练习的材料变了。

网站保存“开始时的数据”和“现在的数据”，还可以报告两者有什么变化。这份变化记录叫 `diff`。例如，开始时没有新发出的任务邮件，现在出现了符合要求的邮件，判分程序便有具体数据可查。它仍需核对收件人、内容和附件；“邮件列表变了”本身不能证明做对了。

多个 Agent 同时做题时，每次尝试使用独立编号 `sid`。这个编号使数据修改、附件上传、重置和判分都对应同一次练习，避免一个 Agent 发的邮件出现在另一个 Agent 的电脑里。这就是“会话隔离”。

下面是实现这些功能的接口。API 可以理解为给脚本使用的读写入口；普通任务执行者仍通过网页界面操作。

| 接口 | 直接理解为 | 用途 |
| --- | --- | --- |
| POST /post?sid=… | 写入或重置这次练习的数据 | 准备材料、建立正确结果、重新开始 |
| GET /go?sid=… | 读取开始时的数据、现在的数据及变化 | 给判分程序检查操作结果 |
| GET /state?sid=… | 只读取现在的数据 | 不需要比较前后时直接检查 |
| POST /upload?sid=… | 上传这次练习的附件 | 文件按练习编号隔开，重置时清理 |

写入时要区分 `set` 与 `set_current`：前者写开始时的数据，后者只写现在的数据、保留起点。若把完成后的数据写成起点，比较前后就看不到任务变化了。

变化记录还排除了浏览时间、界面缓存等容易自动改变的字段。普通对象逐字段比较；列表只要任一位置改变，就把整个列表记为变化。因此，判分程序还需在改变后的列表中找到正确客户、邮件等条目，不能仅因列表变化就加分。

这套方法允许 Agent 用不同的点击路线达到同一个结果，判分程序检查实际结果。过程是否造成破坏，单看最终数据仍无法完全判断。依据：Figure 3，PDF 第 5 页；附录 B.3、B.5，PDF 第 25–27 页。

### 3.9 整理好的一道题，怎样用于训练

通过检查后，一道题会保存为一个目录。里面有任务说明、准备初始电脑的脚本、准备正确结果的脚本、判分脚本和相关配置。配置告诉运行程序该用哪种电脑镜像、从哪个保存的起点恢复、看截图还是其他观察信息，以及最多允许操作多少步。格式沿用 OSWorld 的运行与评测约定。

这些题可以用于两种训练：

- **先看示范，学习操作。** 让较强 Agent 做题，保留成功尝试中的截图和动作，训练模型学习这些操作。这叫监督微调，简称 SFT。
- **自己尝试，根据分数改进。** 让正在训练的 Agent 从初始电脑反复尝试，每次用判分程序打分，再据此更新模型。这叫强化学习，简称 RL。

因此，**题目与操作记录是两个不同的东西**：题目提供起点、要求和判分；操作记录是在这道题上真正尝试之后才产生的。用于测试判分的“正确完成后”电脑，也不等于一份点击步骤的示范。

长任务会产生很多截图和动作。论文把一次操作记录切成多个训练片段，保留任务说明、近期截图和动作，把较早的截图折叠为占位符，以控制模型每次需要处理的内容量。这处理的是如何使用操作记录，与前面如何生成题目是两个层次。

依据：附录 A.6，PDF 第 20–21 页；正文第 3.1 节、Figure 4，PDF 第 5–6 页。

## 4. Experiments：证据支持了什么

### 4.1 数据规模与主要结果

原文正文报告 32,112 个可验证任务包，覆盖 110 个环境：16 个桌面应用和 94 个网页 mock。第 3.1 节主实验使用其中 10,858 个任务包，覆盖 80 多个环境，另有 3,578 条成功教师轨迹作 SFT warm-up。**发布任务总数、主实验 RL 子集和 SFT 轨迹数是三个不同数字。**

| 模型 | OSWorld-Verified 论文所列基座 → CUA-Gym 模型 | WebArena 论文所列基座 → CUA-Gym 模型 |
| --- | --- | --- |
| Qwen3.5-35B-A3B | 54.5% → 62.1%（+7.6 个百分点） | 40.8% → 44.5%（+3.7 个百分点） |
| Qwen3.5-397B-A17B | 62.2% → 72.6%（+10.4 个百分点） | 54.0% → 56.0%（+2.0 个百分点） |

数字来自 Figure 5(b)，PDF 第 6 页。最终模型经历 SFT warm-up 与 RL，表格中的基座对比不能单独拆出 SFT 和 RL 各自的贡献。WebArena 的站点与训练 mock 不重合，结果支持跨环境迁移，但不代表任意线上软件的可靠性。小模型部分域仍退步，例如 Chrome、Thunderbird 和 VLC；总体提升不等于每类操作都提升。

### 4.2 任务量扩展与环境扩展分别怎样验证

![固定 SFT 初始化后的 RL 数据量对照。来源：原论文 Figure 7，PDF 第 8 页。](images/data-scaling.png)

读图要点：比较 1.4K、3K、12K 任务包的 RL 训练，左侧是评测表现，右侧是训练奖励；两种指标需要同时观察，单看训练奖励不足以判断迁移效果。

第 4.1 节固定 SFT 初始化与训练超参数，用 1.4K、3K、12K 任务包训练 A3B。12K 的 OSWorld 曲线整体更高，支持已研究范围内扩大任务量有收益。训练曲线仍有波动，不能把正文“monotonically”理解为每个点都严格单调；它也不能证明再放大任意倍数仍保持相同收益。

第 4.2 节因为逐环境 RL 消融成本高，改用成功教师轨迹进行标准 SFT：

![教师轨迹 SFT 下的环境规模与数据量对照。来源：原论文 Figure 8，PDF 第 8 页。](images/environment-scaling.png)

读图要点：前两根柱固定轨迹总量比较环境覆盖，后两根柱固定环境覆盖比较轨迹量；这一图使用 SFT，与上图的 RL 数据量实验属于不同协议。

| 环境数 | 教师轨迹总数 | OSWorld-Verified |
| --- | --- | --- |
| 10 | 3K | 57.8% |
| 80 | 3K | 58.8% |
| 80 | 6K | 60.7% |

10→80 个环境、固定 3K 轨迹增加 1.0 个百分点，直接支持该 SFT 设置下环境多样性的作用；80 个环境、3K→6K 轨迹增加 1.9 个百分点，支持固定环境覆盖时更多轨迹的作用。首尾比较同时改变两者，不能把全部 2.9 个百分点归因于环境多样性。依据：第 4.1、4.2 节与 Figures 7、8，PDF 第 7–9 页。

### 4.3 验证与成本证据的强度

附录报告多数审查约去掉 3,100 个样本，教师筛选再去掉 1,278 个。这表明内循环通过后仍会遇到静态规格和实际操作问题；这些数字不是奖励误判率，也不能据此得到信息隔离的净贡献，因为没有相应的关闭隔离对照。

原文同时观察到 RL 后每个模型 step 的工具调用增加到约 1.4–1.9，匹配任务表现时轨迹缩短 33–45%。作者将其解释为固定 step 预算下对确定性操作链的批处理选择，属于行为观察与机制解释，不能推广为所有任务都应该减少视觉检查。依据：附录 A.4.3，PDF 第 18 页；第 4.3 节与 Figure 9，PDF 第 9 页。

## 5. 结论边界与我的判断

**原文支持的结论：** 在当前实验范围内，自动准备并检查的操作题能够用于训练电脑操作 Agent，并改善桌面和未用于训练的浏览器评测成绩。训练网站可以反复用于出题；增加题目数量和软件种类分别有相应的实验支持。

**原文明示的限制：** 奖励检查终态，不能判断是否通过破坏性过程重建了同一结果；信息隔离和扫描降低但不彻底消除奖励漏洞；mock 不覆盖认证、真实集成、网络延迟、限流与罕见服务端故障；最大规模 RL 由于成本只有单 seed。依据：第 6 节，PDF 第 10 页。

**判断：** 这篇论文最可借鉴的是把不同问题分开检查：是否漏了某类操作、材料能否准备好、两个测试结果是否判对、题目是否说清，以及实际操作是否完成。自动判分适合大量训练，但仍要看它具体检查了什么，是否会接受错误结果。

数据量与复现参数还有几处限制：

- **任务总数。** 正文与 Figure 6(c) 是 32,112，Figure 6(b) 中心写成 32,122。本文采用正文反复报告的 32,112。
- **每应用配额。** A.2.5 声称每应用至少 1,000 个 verified tuples；若 110 个环境都按此执行，至少应有 110,000，无法与正文总量直接吻合。该配额不能当作已实现的数据分布。
- **叶子覆盖。** A.2.3 写每叶至少 25 个任务，A.2.6 又写第一轮每叶两个指令满足覆盖最低要求；文内未清楚解释两种粒度的关系。
- **多数票公式。** A.4.1 描述“严格多数”却写 `ceil(V/2)+1`。奇数 V 时它比通常的 `floor(V/2)+1` 多一票；且未给出 V，无法确认实际代码阈值。
- **筛选配置。** A.4.2 没有列出 Nteach 与 δ，也未穷尽所有均值组合的处理方式，不足以精确复现。

这些文本差异不能直接证明实现错误；复现时应以实际代码与数据配置为准。

## 6. 开放问题

- **怎样更可靠地拒绝错误结果？** 除了“还没做”和“正确完成”两种情况，能否故意准备错收件人、漏步骤、空附件和错误数据，检查程序是否会错误地给分？
- **会不会把可做的难题筛掉？** 较强 Agent 失败的任务中，有多少真的做不到，有多少只是它能力不足或步数不够？
- **改写指令会不会降低要求？** 为了让任务通过筛选而改写说明时，怎样保证没有删掉原本需要完成的步骤？
- **训练网站与真实应用差多少？** 除了检查网站符合开发说明，怎样独立评估它是否遗漏真实软件的重要功能，以及登录、网络和权限问题会怎样影响操作？
- **最终结果正确，过程是否也合理？** 如果 Agent 删除原内容再重新建立同样结果，只检查最后的数据可能发现不了中间的破坏。
